# フェーズフリーアプリへの防災計画・業務実行支援の統合方針

作成日：2026-10-18  
状態：P0は2026-10-18、P1（実施記録の循環・保存/復元・未割当理由・見直し候補）は2026-10-19に実装。操作・実装・検証は [P1実装ノート](phase-free-p1.md) を参照。原文PDF取込み・文書の横断照合・追加AIツール等はP2以降の実装計画。

## 1. 採用する方針

**既存の点検・事前対策・復旧機能を、計画の根拠と共通の業務定義でつなぐ。**

```text
地域防災計画・実施マニュアル・協定
          ↓ 根拠の特定と自治体への適用確認
共通の業務定義 ←→ 施設台帳・管理者・利用可能な資源
          ↓
平時の点検・事前対策 → 災害時の点検・再計画 → 実施結果の記録
          ↑                                  ↓
台帳・点検条件の更新 ← 見直し候補 ← 未実施・不足・実績の検証
```

初期対象は、実証自治体が管理する道路と付属構造物の平時巡回・地震後点検・結果報告とする。橋梁、道路法面・盛土等の既存資産に接続する。国・県・民間の管理施設については、管理者への照会・連携という業務を定義する。

実証自治体は未選定。デモ用の仮の部署・担当と、自治体から確認した実際の組織・管理範囲を区別して扱う。計画体系に加えて、管理権限と対象施設を決めることで、市町村業務としての実証範囲を確定する。

## 2. 既存アプリの接続点

確認対象：`index.html`、`README.md`、`tests/smoke.js`、`tools/fetch_kumamoto_event.py`、発災後データのmanifest。

次の「現状」は統合設計時（2026-10-18）の状態を記録したもの。P1では案件別履歴、判断時点での基準状態の取得、非同期ツールの待機、IndexedDB保存等を追加した。

| 接続先 | 現状 | 統合する内容 |
|---|---|---|
| `AS` / `addAsset()` | `a.id`と配列添字`a.i`で施設を管理 | 業務・記録は資産IDで結合し、配列添字への変換はアダプターに限定 |
| `TYPES[type].dept` / `a.town` | 部署名は種別の仮設定、町は最寄り代表点による対応 | 管理者・実施機関・正式な自治体コードを別属性として登録 |
| `S` / `setPhase()` | モード切替で確認記録や必須指定等をクリア | 継続する台帳・業務定義と、案件別の実行状態・表示モードを分離 |
| `makeDPlan()` / `tabDPlan()` | 想定地震、予算配分、初動拠点を比較 | 「事前対策」として、どの計画項目・業務に対応する対策かを表示 |
| `scoreNormal()` / `posterior()` | 平時状態を直接参照し、発災後は生成時の`a.p0`を使用 | 判断時点で参照できる点検履歴から基準状態を取り出し、入力版に対応した優先度・事前確率を計算 |
| `compute()` / `planRoutes()` | 施設単位の優先度、班・時間・通行条件で巡回案を生成 | 業務から点検対象を作り、作業項目・所要時間・未割当理由を接続 |
| `tabPlan()` | 施設と訪問順を表示 | 各訪問先に業務ID、確認項目、根拠、実施状況を表示 |
| `tabWhy()` / `explain_asset` | 被害推定・点検優先度の根拠を表示 | 「なぜ確認対象か」に加え「どの計画・手順に基づき何を確認するか」を表示 |
| `injectNext()` / `S.confirmed` | 現地確認の投入をシナリオとして再現 | 合成の投入と職員入力を区別した構造化記録へ接続 |
| `AI_TOOLS` / `ruleSteps()` | 簡易ルールとClaude経路から同じ機能を呼ぶ | 文献検索、実施手順照合、業務候補、改定候補のツールを追加 |
| `aiRunTool()` | ツール本体を同期実行して結果を記録 | 保存・検索の非同期処理を扱えるよう実行部を拡張 |
| `log()` / `tabMetrics()` | メモリ内の操作ログ、合成真値による評価 | 案件・業務・文献版に紐づく実施記録と評価結果を保持 |
| `syncEvData()` | 埋込み索引とHTTP配信時のmanifest同期 | 文献も版付きの配布パッケージを用意し、ローカル閲覧に対応 |

特に、現在の`S.must`は優先度への加点であり、時間内の割当を保証する制約ではない。業務上必要な点検は、未割当の場合も残し、原因を表示する設計にする。

## 3. 画面構成

### 常時表示の「計画・業務」を追加する

新しいタブIDは`rplan`とし、平時・発災後の双方で表示する。タブ内に次のビューを持たせる。

| ビュー | 主な表示・操作 |
|---|---|
| 根拠資料 | 資料の正式名称、版、適用範囲、章節、原文、PDFページへのリンク、本文確認状況 |
| 整合性・実施準備 | 法令上の記載不足候補、文書間の不整合、実施手順未確認、資料未提供、適用対象外 |
| 業務一覧 | 業務内容、対象施設、担当、開始条件、必要資源、先行作業、点検計画への接続、実施状態 |
| 見直し候補 | 実績・未実施理由・訓練結果から作る改定候補、変更前の記載、変更案、根拠記録 |

既存の`dplan`の表示名は「事前対策」に整理する。内部ID・`prevention_plan`というツール名は接続を保ち、説明文・AI回答・ログ・画面遷移の表示名をそろえる。

「点検計画」「根拠追跡」「復旧計画」「評価指標・ログ」は、同じ業務IDと実施記録を参照する。計画文書上の業務から地図上の施設へ、施設から根拠条項へ相互に移動できる構成にする。

## 4. 共通データモデル

文書の要件、自治体向け業務定義、個々の作業実績を別のレコードとして保持する。

| レコード | 主な項目 |
|---|---|
| `DocumentVersion` | 文書ID、版ID、正式名称、文書種別、発行主体、対象地域、改定日、公表日、適用期間、取得日時、原URL、ローカルファイル、SHA-256、抽出・確認状況 |
| `Section` | 版ID、章節ID、PDFページ番号、紙面記載ページ、原文、引用位置、確認状態 |
| `Requirement` | 要件ID、根拠章節、要件の説明、法令上の義務・計画上の方針・実施手順・研究上の提案の区分、適用条件、照合先 |
| `TaskDefinition` | 業務IDと版、要件ID、対象資産条件、実施機関、協力機関、平時・災害時の開始条件と確認項目、必要資源、標準作業時間、先行業務、完了条件 |
| `AssetReference` | 資産ID、外部台帳の識別子、管理者、実施機関、自治体コード、管理範囲の確認状況、実・合成の別 |
| `Case` | 案件ID、平時点検・訓練・災害対応の別、対象地域、災害・シナリオID、判断時点、採用文書版の集合 |
| `TaskRun` | 実行ID、案件ID、業務定義の版、資産ID、開始根拠となる事象ID、割当班、予定時刻、状態、未実施理由 |
| `Observation` | 記録ID、実行ID、観測・実施日時、登録日時、記録者、確認項目、所見、資料参照、実・合成・推定の別 |
| `RevisionProposal` | 候補ID、変更対象の文書版・章節、変更前の記載、変更案、理由、根拠となる実施記録、アプリ内の確認状況 |

### IDと版の扱い

- 初期の資産結合には既存の`a.id`を使用し、外部台帳IDとの対応表を保持する。`a.i`、施設名、最寄りの町名は永続的な参照キーにしない。
- 実行時に業務定義と文書版を固定する。後で資料が更新されても、過去の判断根拠を差し替えない。
- 同じ業務定義を平時と災害時で使うが、平時に完了した点検と発災後の再点検には別の実行IDを付ける。
- 再計画だけでは作業を重複生成しない。案件・開始事象・業務定義版・資産の組を重複防止の単位にする。
- 表示のモード切替と、案件の新規作成・シナリオのやり直しを別操作にする。

### 日時の扱い

判断時点の制御には公表・利用可能日時を使う。取得日時、改定日、観測日時、点検年度をそのまま利用可能日時に読み替えない。適用日や公表日が未確認なら、その状態を保持する。

## 5. 文献を業務へつなぐ方法

### 入力資料の位置付け

| 資料 | アプリでの用途 |
|---|---|
| 防災基本計画 | 国の基本方針、計画間の関係、重点事項の根拠 |
| 国土交通省防災業務計画・第16編「地域防災計画の作成の基準」 | 公共土木施設の予防、緊急点検、復旧等の根拠 |
| 熊本県地域防災計画・本編／資料編 | 県の対応と広域連携、関係機関、手順・資源の参照 |
| 対象市町村の地域防災計画・マニュアル・協定 | 市町村の担当、開始条件、確認方法、報告先、資源の確定 |
| 地区防災計画ガイドライン・ガイドブック | 住民・事業者との協働、計画提案、訓練・見直し機能の設計 |
| 防災基本計画添付資料 | 背景情報・想定の参照。個別施設の現状とは分ける |
| 内閣府防災業務計画 | 内閣府の業務・国との連携の参照。自治体の担当を直接決める資料とは分ける |
| 指定公共機関の防災業務計画のHTMLページ | 各機関の計画への索引。参照先の本文取得状況を別に管理 |
| i003の手引き抜粋 | 計画づくりのプロセスの参考。資料の発行年・手続の適用時点を確認して用いる |
| 災害対策基本法等の該当条文 | 法令上の義務、適用条件、根拠の照合 |

正式名称・版は原資料と掲載元で確認する。ファイル名やURLに含まれる年月だけで判断しない。国交省資料の掲載元は https://www.mlit.go.jp/saigai/bousaigyoumukeikaku.html 。

### 取込みと構造化

1. 原資料を保存し、原URL・取得時刻・SHA-256を記録する。URLの中身が更新されても旧版を保持する。
2. PDFは前処理でページ単位に抽出し、章節・紙面ページ・原文を対応付ける。本文が抽出できないページは要確認として残す。
3. 初期MVPは確認済みの条項と業務定義を小さく登録する。全文取込みの拡張時も、機械抽出と人が確認した根拠を識別する。
4. 原文の記載と、アプリが具体化した確認項目・提案を別フィールドにする。県計画から作った仮の手順を、市町村の正式手順として表示しない。
5. 対象自治体・施設管理者・災害種別・時点を指定した上で、本文、資料編、マニュアル、協定を横断して照合する。

照合結果は`covered`（対応記載確認）、`missing_candidate`（記載不足候補）、`conflict`（不整合候補）、`unverified`（手順未確認）、`document_not_provided`（資料未提供）、`not_applicable`（適用対象外）を区別する。資料未提供や抽出失敗を、手順の不存在と判定しない。

## 6. 点検・記録・見直しへの接続

### 初期の代表フロー

1. 職員が「道路施設の状態確認」の根拠、対象、担当、確認項目を「計画・業務」で確認する。
2. 平時は点検周期・未解決の所見から実行候補を作り、既存の点検計画へ渡す。
3. 地震対応の案件を開くと、同じ施設と業務定義から緊急点検の実行候補を作る。平時の点検結果も参照する。
4. 通行止め、班数、稼働時間、作業時間を反映して訪問順を更新する。各訪問先に根拠と確認項目を表示する。
5. 点検結果と実施できなかった理由を登録し、未確認・追加調査・完了を更新する。
6. 未解決の連絡先、資源不足、実施手順の曖昧さ等から、根拠記録付きの見直し候補を作る。
7. 確認された点検・補修実績を、次回の平時点検条件へ反映する。

### 平時記録を計算に反映する

判断時点で参照可能な記録から基準状態を返す処理を設け、`scoreNormal()`の点検時期・状態の入力へ接続する。災害時も、その案件の時点で使える基準状態から事前確率を計算する。現在の`a.p0`は施設生成時に計算済みのため、記録を保存する機能だけではこの計算は更新されない。

入力に採用した所見・点検日時、モデルの設定、未確認の項目を計画のスナップショットに保存する。業務の完了状態と施設の損傷状態は別に扱い、「記録なし」を「異常なし」に変換しない。平時記録の有無による比較でも、この同じ計算経路を使う。

### 計画生成の扱い

- 業務の対象条件と管理者の対応を確認してから、施設をルート生成へ渡す。管理者未確認の施設は照会業務として残す。
- 最初のMVPは同一案件・同一施設の状態確認をまとめた訪問単位とする。確認項目と業務IDの対応は訪問単位の内側に残す。
- 作業時間は訪問単位の確認内容から計算し、`planRoutes()`の種別別固定時間に接続するアダプターを追加する。
- 予定に入ったことと、実施が完了したことを区別する。到達不能、時間不足、担当班不足、必要情報未確認は未割当・保留理由として返す。
- 作業順や資源制約の検査はプログラムで行い、LLMには根拠の抽出・説明・下書きを担当させる。
- 復旧計画で終了予定日が到来しても、実績記録がなければ復旧完了として台帳を書き換えない。

既存の計画版ごとの確認操作と連携する。アプリ内の確認状態と、法定計画の策定・修正・報告・公表の実施記録は別属性で管理する。

## 7. AIツールへの組込み

| ツール／接続先 | 拡張内容 |
|---|---|
| `plan_search`（追加） | 対象自治体・時点・文書種別を指定して根拠条項を検索。版、章節、原文、ページを返す |
| `plan_review`（追加） | 適用条件と資料の充足状況を踏まえ、照合結果と確認先を返す |
| `operational_tasks`（追加） | 業務候補、実行状況、必要資源、未割当・保留理由を返す |
| `revision_draft`（追加） | 実施記録と変更対象の章節に結び付けた改定候補を返す |
| `get_status`（拡張） | 案件、判断時点、使用文書版、未完了業務を追加 |
| `inspection_plan`（拡張） | 業務の実行IDを受け取り、訪問先と実行IDの対応を返す |
| `explain_asset`（拡張） | 施設の分析根拠に加え、該当業務と計画・手順の根拠を返す |

簡易ルール側では、「地域防災計画の整合確認」「業務・担当・報告手順」「予算を伴う事前対策」を区別する。現状の`/防災計画/`による事前対策生成との競合を解消する。

Claude経路にも同じツールを公開する。ツール数制限がある場合は、`AI_TOOLS.slice()`で先頭だけを渡す方式から、依頼に必要なツールを選ぶ方式へ拡張する。入力スキーマ、対象ID、文書版の検証を実行側にも置く。

`aiRunTool()`は非同期ツールを待機できる形にし、検索・保存の完了または失敗を実行トレースへ残す。回答には原文の引用とアプリによる提案を表示する。

既存の`checkReport()`は文章構成と数字の照合を担う。根拠ID・版・ページ・引用の一致は追加の検査とし、内容が業務に適合するかは根拠レビューの記録で管理する。

## 8. 実装構成と保存

### 提案する追加ファイル

```text
bousai_plan_data/
  manifest.json                  文献の原URL・版・ハッシュ・抽出状況
  sources/                       版別の原PDF・法令等
  sections.json                  ページ・章節と原文
  requirements.json              適用条件付きの要件
  task_definitions.json          共通業務定義
  demo_cases.json                 デモ案件と入力条件
  app_bundle.js                  ローカル閲覧用の生成済みデータ
js/
  plan-core.js                   照合、業務生成、ID対応、状態更新の純粋処理
  plan-storage.js                案件・実施記録・スナップショットの保存
  plan-ui.js                     計画・業務タブと既存画面への表示アダプター
tools/
  fetch_bousai_plans.py          原資料の取得・版別保存
  preprocess/bousai_plans.py     PDF抽出・構造化・配布データ生成
  build_phase_free_demo.py       JS・条項データを埋め込んだ単一HTMLの生成
tests/
  plan_core.test.cjs             適用条件・状態・重複防止等の検証
  test_bousai_plans.py           文献の版・ページ・抽出状態の検証
```

初期版は通常の`script`で生成済みデータと小さなモジュールを読み込む。`index.html`から既存の状態・資産・ルート計算をアダプター経由で渡す。PDF抽出を前処理に置くことで、`file://`とHTTPの両方で計画・業務の画面を使える構成にする。

既存の単一HTML配布とClaude Artifactでの利用には、同じJS・確認済み条項を埋め込む生成処理を用意する。原PDFは文献パッケージまたは出典URLから参照する。Artifact向け生成物では本文・引用を内部で参照できるようにし、`window.claude.use("sample")`経路は利用可能な環境で動作を検証する。

案件、実施記録、改定候補、計画作成時の入力スナップショットはIndexedDBに保存し、JSONの書出し・読込みを提供する。ブラウザで保存できた状態を表示し、再読込み時に復元する。原PDFは文献パッケージから参照する。

実証で自由文検索・PDF追加取込みを拡張する段階で、前処理とLLMを呼ぶバックエンドへ接続する。検索・照合・業務生成の入出力形式はローカル版とそろえる。共同利用段階では、同じID・版のモデルをサーバーの永続ストアへ移す。

## 9. 実装順序と完了条件

| 段階 | 実装内容 | 完了条件 |
|---|---|---|
| P0：根拠付き業務MVP | 文献・業務定義・案件のモデル、確認済み条項の登録、常時表示の「計画・業務」、既存点検計画への接続 | 道路施設の点検について、原文→業務→施設→訪問先→根拠の一往復を画面で追える。対象自治体や管理者の未確認状態も表示できる |
| P1：平時・災害時の記録循環（実装済み） | 案件別の状態、構造化点検記録、モード切替時の履歴保持、保存・復元、未割当理由、記録からの見直し候補 | 平時の実績を災害案件から参照でき、発災後の点検は別実行として残る。再計画・再読込みでも記録が失われず重複しない |
| P2：文書照合・改定支援 | PDF前処理、資料編・マニュアル・協定との横断照合、条件付き要件、改定候補、新AIツール | 資料未提供と記載不足候補を区別し、指摘と変更案から原文・実施記録へ遡れる |
| P3：自治体実証・運用拡張 | 実証自治体の正式資料・組織・管理資産・資源を接続、LLMバックエンド、共同利用、評価 | 専門家・担当者による評価と平時記録の有無による比較結果を残せる。地区防災計画の意見・提案機能は、この共通基盤に接続して拡張 |

P0を最初の実装単位とし、P1で一巡するフェーズフリーの操作を完成させる。P2・P3で入力文書と実証範囲を広げる。

## 10. 検証計画

### 機能の検証

- 関連マニュアルに手順がある場合は、本文の記載不足候補と重複させず対応先を表示する。
- マニュアル未提供、本文抽出失敗、適用対象外、担当未確定をそれぞれ別の結果にする。
- 文書の更新後も過去の実行記録が旧版を参照し、案件の判断時点より後の情報を自動採用しない。
- 同じ事象の再投入・再計画で実行を重複生成せず、別の地震・再点検事象では新しい実行を作る。
- モード切替・再読込み・JSON書出し／読込み後も、記録と参照関係を復元できる。
- 到達不能、担当班なし、時間不足の業務を落とさず残し、完了扱いにしない。
- 同一施設の複数確認項目を訪問単位にまとめても、業務ごとの根拠と完了条件が保持される。
- 合成の現地確認投入と実際の職員入力を、記録と表示の双方で区別する。
- AIの指示が文書照合を求めている場合に、予算配分の事前対策へ誤って送らない。
- ローカルファイルとHTTP配信の双方で新画面を操作し、既存の点検・事前対策・復旧・データ索引の画面も確認する。
- 平時の点検記録が優先度・災害時の事前状態に反映され、判断時点より後の記録は反映されないことを確認する。
- 単一HTML生成物が同じ文献版・業務定義を持ち、外部のローカルJSに依存せず画面を表示できることを確認する。

既存の`tests/smoke.js`の画面確認に、新しい一連の操作と参照関係のアサーションを追加する。追加チェックの不成立は終了コードに反映する。

### 研究・実証の評価

| 観点 | 指標と比較 |
|---|---|
| 文書照合 | 専門家が確認した正解に対する適合率・再現率、重要な見逃し、引用の正確性。資料未提供と適用対象外を区別して集計 |
| 業務の具体性 | 担当・開始条件・資源・完了条件の充足、職員の修正量、案作成の所要時間 |
| 実行可能性 | 資源・通行・時間制約の違反、優先対象の確認達成率、未割当理由、再計画時間 |
| フェーズフリー性 | 同じ案件・資源条件・手法で、平時点検履歴を使う条件と使わない条件を比較 |
| 記録からの改善 | 見直し候補の根拠追跡率、担当者が妥当と判断した候補、次回点検への反映状況 |

比較用の実行では、参照可能な時点と入力スナップショットを固定する。事後の被害確定情報を初動入力へ混ぜない。デモの合成真値に対する指標と、自治体職員・専門家による評価を別の結果として表示する。

## 11. 実装着手時に確定する入力

- 実証自治体と対象道路・施設の管理範囲。
- 市町村計画、資料編、点検要領、初動マニュアル、報告様式、応援協定の提供状況。
- 実施機関、連絡・報告先、班編成、作業時間、資機材の実データ。
- 文献の適用版・公表日時と、業務定義の確認担当。

これらは設定・資料充足状況として画面に残し、初期デモでは未確定の項目を明示してP0の実装を進める。

## 12. P1の実装結果（2026-10-19）

- `js/plan-core.js` に案件・開始事象・共通業務版・施設IDで一意な実行、追記型の実施記録、時点制御、未割当理由、見直し候補、JSON参照整合性の検証を実装。
- `js/plan-storage.js` と `js/plan-ui.js` でIndexedDB保存、起動時の復元、JSON入出力、保存状態、案件・再点検の明示的な開始操作を接続。
- `scoreNormal()` と `posterior()` は採用可能な職員入力の所見から基準状態を取得し、平時の点検条件と災害時の事前確率を更新する。発災後の所見を初動の事前確率へ遡及させない。
- 現地確認のシナリオ投入・公開速報は、職員入力と異なる出所として保存。時系列を巻き戻しても将来の記録を保持し、同じ投入の再実行では重複させない。
- 計画の訪問先から担当・確認項目・作業時間・資源・実施記録・固定した参照記載へ移動できる。計画入力とモデル設定をスナップショットとして残す。
- 実施記録・未割当理由から見直し候補を作成し、確認者と反映内容を保存。新たな根拠の追加時は再確認対象を表示する。
- 文献・条項はP0の仮要旨・未確認状態を継続して明示。文書の更新で過去の実行が参照した記載を差し替えない。
- `tools/build_phase_free_demo.py` で3モジュールを単一HTMLに埋め込み、`--check` で配布物とソースの一致を検証できる。

検証は `tests/plan_core.test.cjs`、`tests/plan_p1.cjs`、既存の `tests/smoke.js`。P1操作の `file://`・HTTP双方、IndexedDBの再読込み、JSON往復・不正入力、保存エラー、時点・版の固定を対象とする。詳細な操作とデータ項目は [P1実装ノート](phase-free-p1.md) に記載。

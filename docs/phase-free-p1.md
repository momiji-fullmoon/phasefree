# P1：実施記録を平時・災害時の計画へ循環させる

実装日：2026-10-19。対象は既存のフェーズフリーHTMLアプリ。

## 操作の流れ

1. **「計画・業務」**で案件・判断時点を確認する。初期案件は平時 `C-NORM` と地震対応 `C-EMG`。
2. **「業務一覧」または「点検計画」→「実施記録」**を開く。記録者、実施日時、利用可能日時、確認項目、所見を入力する。
   - 「点検完了」には全確認項目の確認が必要。
   - 損傷の「未確認」と「異常なしを確認」を区別する。
   - 未実施や追加調査も保存できる。未実施理由と自由記載の所見を残す。
3. **健全度付きの職員入力を基準状態へ採用**すると、平時の点検優先度が更新される。発災後のモードでは、発災前に利用できた所見から事前確率を計算し直す。
4. **平時／発災後の切替**で各案件の時点・班・対象・実施記録を再表示する。切替で履歴を消さない。
5. **「未割当・保留」**で、担当班なし、到達不能、時間不足、探索候補上限、必要情報未確認などを確認する。管理者・管轄の照会は現地点検とは別業務で残す。
6. **「見直し候補」**で、所見・未実施記録・計画入力へ戻り、確認者と確認・反映内容を記録する。
7. 保存状態を確認する。**「JSON書出し／読込み」**で別ブラウザ・別URLへ移すこともできる。

## 案件・実行・観測の区別

| データ | 扱い |
|---|---|
| 共通業務定義 | 道路施設は `T-ROAD-01@demo-inspection-v1`。平時と災害時で同じ定義を採用 |
| 画面上の業務名 | `T-OPEN-01`／`T-EMG-01` はフェーズ別の表示名として継続 |
| 業務実行 `RUN:…` | 案件ID・事象ID・共通業務ID・定義版・資産IDの組で一意。再計画では増やさない |
| 実施記録 `OBS-…` | 実行への追記。職員入力・合成のシナリオ投入・公表資料の暫定判読を区別 |
| 計画入力 `SNAP-…` | 判断時点、文献版、採用所見ID、健全度、点検年、耐力・事前確率、モデル設定、割当、未割当理由を固定 |
| 見直し候補 `REV:…` | 案件・業務・理由でまとめ、実施記録ID・計画入力ID・文献版・参照記載と結ぶ |

**予定への割当は実施完了ではなく、業務完了も「損傷なし」の代用にはしない。**

「同じフェーズで別案件を作る」は現在の地震・平時シナリオ用の別案件を作成する。「現在時点で再点検を開始」は同じ案件に別の開始事象を作る。どちらも旧実行と旧記録を残す。

発災後の「発災直後に戻す」は、同じ案件の表示時点を巻き戻す。後の時点の記録を消さず、計算への採用から外す。同じ `F1`／`F2`／調査速報を再投入しても記録を重複生成しない。

## 時点と基準状態

- 実施日時、利用可能日時、実際の登録日時を別属性で保存する。画面入力はJST。
- 判断への採用は**実施日時と利用可能日時の両方が判断時点以前**であることが条件。登録日時を利用可能日時の代用にはしない。
- 平時の基準状態は、健全度付き・点検完了・基準状態への採用指定がある**職員入力**から決める。合成投入や暫定判読では基準状態を更新しない。
- 災害時の事前確率へ採用する記録は、発災日時より前に実施・利用可能だったものに限定する。災害後に得た所見は、初動の事前確率へ遡及させない。
- 発災後の健全度も、採用指定があり、その利用可能日時以後を平時の判断時点に設定した場合は、次回点検の基準状態として参照できる。
- 記録を追加しても合成真値や既存の台帳を直接上書きせず、同じ基準状態取得処理から優先度・確率・表示を更新する。

## 未割当と見直し

各部局の上位30候補という既存の探索上限を明示し、**探索候補数上限**と**時間不足**を分ける。候補閾値未満、担当者による除外、事象が判断時点より後の場合も、理由付きの実行として残す。

管理者・管轄・連絡先の未確認は、照会業務 `T-COOP-01` の「必要情報未確認」として保持する。現地点検の班・対象・確認項目はデモ設定であり、正式な管理権限を確定した表示にはしない。

見直し候補は、未実施・追加調査・継続所見・損傷未確認の記録や、班・時間・情報不足などの計画結果から生成する。状態は「候補／確認済み／反映記録済み（アプリ内）／採用しない」。確認者・内容を保存し、新しい根拠が追加された場合は「新しい根拠あり」と表示する。法定計画の改定・承認・公表を自動実行した状態とは分ける。

原文・適用版が未確認の資料は、その状態と仮要旨を表示する。実行時の文献版・参照記載を保持し、資料データの更新で過去の参照記載を差し替えない。PDF本文の取込み・横断照合はP2の対象。

## 保存と復元

- IndexedDB：DB名 `kumamoto-phase-free-p1`、`workspace/current` に案件・実行・観測・見直し・計画入力・表示条件を保存する。
- 保存の順序を直列化し、最新の保存処理が完了したときに「ブラウザ保存済み」を表示する。
- 起動時に保存形式・参照整合性を検証して復元する。保存不能・容量不足・復元失敗を、保存成功として表示しない。
- ブラウザ保存が使えない場合も、メモリ内の記録とJSON書出しを使える。
- JSON形式：`format: "kumamoto-phase-free-plan"`、`version: 1`。状態には `schemaVersion: 1` を持つ。入力は64MBまで。
- JSON読込みは形式・ID重複・施設・案件・事象・文献版・実施日時・確認項目などを先に検証し、不正な入力では現在の記録を置き換えない。正常な読込みは案件一式の復元で、他の記録との自動マージではない。
- 写真本体は保存パッケージに含めず、ファイル名・資料IDなどの参照を保持する。

ブラウザの保存領域はURLのオリジンごとに分かれる。`file://`、`http://localhost:8000`、`http://127.0.0.1:8000` の間の移動にはJSON入出力を使う。

## 実装と検証

```text
js/plan-core.js                  案件・重複防止・時点制御・履歴・見直し・JSON検証
js/plan-storage.js               IndexedDBのトランザクション保存
js/plan-ui.js                    既存計算への接続、実施記録・案件・見直しの画面
tools/build_phase_free_demo.py   3ファイルをindex.htmlへ埋込み
tests/plan_core.test.cjs         データ・時点・重複・版固定・JSONのテスト
tests/plan_p1.cjs                file://とHTTPの操作・保存・復元・異常系テスト
```

配布する `index.html` はJSを埋め込み済みで、外部のローカルJSファイルに依存しない。ソースを編集した後は再生成する。

```sh
python3 tools/build_phase_free_demo.py
python3 tools/build_phase_free_demo.py --check
node --test tests/plan_core.test.cjs
node tests/plan_p1.cjs
node tests/smoke.js
```

ブラウザテストにはPlaywrightとChromiumが必要。既存の点検・事前対策・復旧・データ索引のスモークテストに加え、平時所見による事前確率の変化、モード切替、未実施、見直しへの反映記録、再読込み、JSON往復、不正JSON、合成投入の再実行、再点検、別案件、保存エラー、IndexedDB不使用時を検証する。
